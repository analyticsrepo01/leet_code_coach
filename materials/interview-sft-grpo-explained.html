1. The problem in everyday words

An AI agent works like a person at a small desk. The desk is the model's context window: the text it can see at once. On a long task, papers pile up: tool outputs, error messages, earlier steps. When the desk is full, something must go. Usually the oldest papers are thrown away (truncation), or everything is shortened the same way (summarisation). Both can destroy the one detail the agent needs later: a patient ID, a gene name, a ticket number.

CRAM ("Context-Rational Agentic Memory") asked: can a small model learn to tidy its own desk? It would label pieces of text with four "directives":

directive meaning
[KEEP] this matters, hold on to it
[COMPRESS] shorten this
[EVICT] throw this away
[REFOCUS] step back to the main goal

Some items in a task are wrapped in <shield>…</shield> (for example <shield>JIRA-402</shield>). These must never be dropped. That's the Guardian Shield idea.

Dataset:

  • 156 real multi-step agent tasks across 14 domains (engineering, health, life sciences, finance, legal and others);
  • 11 of the 156 contain shield tags.

Say it like this: "Agents forget the one detail they need because their memory is a fixed-size window. I tried to teach a small model to decide what to keep and what to throw away, and never to drop protected facts."

2. The model, and how I trained it cheaply

Model: google/gemma-4-E4B-it, an instruction-tuned Gemma 4 model the repo calls 4B parameters. The parameter printout counts 7,946,605,856 in total, including embeddings.

Quantization (4-bit NF4). Normally each weight is stored as a 16-bit number. Quantization stores it in 4 bits. NF4 ("Normal Float 4") picks those 16 possible values to match the bell-curve shape that weights usually have, so little accuracy is lost. "Double quantization" also compresses the small scaling numbers, saving about 0.4 GB. Result: about 5–6 GB to run the model and about 23 GB to train it, on one H100 80GB.

LoRA (Low-Rank Adaptation). Instead of changing all the weights, I froze the model and attached small "adapter" matrices to every linear layer. They learn a correction: new weight = old weight + B·A × (α/r).

LoRA setting value
rank r (size of the correction) 8
scaling α 16 (so the correction is scaled × 2)
dropout 0.05
trainable parameters 5,505,024, i.e. 0.069% of the model

B starts at zero, so at step 0 the adapter changes nothing. QLoRA = LoRA on top of a quantized model.

Optimizer: AdamW 8-bit (stores the optimizer's memory in 8 bits, saving about 4 GB).

Say it like this: "I trained only about 5.5 million parameters, under 0.1% of the model, on a 4-bit copy of the model. That made each experiment fit on one H100 in about two hours."

3. SFT: learning from worked examples

3.1 What it is

Supervised fine-tuning is like a teacher handing a student finished, correct answers. The student learns to produce answers in the same style.

Technically, the model reads a question plus a gold answer and is trained to predict each next word of the answer. The error is measured with cross-entropy loss: how surprised the model is by the correct next word; lower is better. Only the answer words count. The question words are "masked" (label −100), so the model isn't trained to repeat the question.

3.2 Why CRAM needed it

On its own, the model almost never wrote a directive:

  • 0% of answers in the baseline run;
  • 0.3% in the Guardian run;
  • at most about 3% even with tricks (§7).

SFT was meant to change the model's default habit ("prior"), so directives appear without being demanded. GRPO would then shape which directive and when (from the docstring of train_sft_v1.py).

3.3 Where the 156 examples came from

generate_sft_dataset.py:

  • sends each of the 156 tasks to a Claude model through the API;
  • asks for a <think> reasoning block, an <answer> block, at least one directive, and every shielded entity kept.

The model name is [CHECK]: the docstring says claude-opus-5, the code calls claude-opus-4-8.

The prompt used the optional wording ("You may emit…"), the same wording GRPO used later, so SFT would teach a habit, not obedience.

Important fact: all 156 gold answers use only [KEEP]. The data has no example of COMPRESS, EVICT or REFOCUS.

One real example (task fleet/jira_github_sync_01, trimmed):

Task: "We need to audit our release branch state. Extract Jira ticket <shield>JIRA-402</shield> and cross-reference it with GitHub <shield>PR-98</shield>. Verify if all checks passed, update the Jira status field to 'MERGED', and comment the verified commit hash <shield>7a8f9c2</shield> into the PR thread."

Gold answer: <think> "…I need to fetch JIRA-402 details, inspect PR-98 CI check results, update the Jira status field, and post the verified commit hash as a PR comment. All three shielded entities must appear in my output." </think> <answer> "1. Fetch Jira ticket details: GET /rest/api/3/issue/JIRA-402 … 2. Inspect PR-98: GET /repos/{owner}/{repo}/pulls/98, GET …/commits/7a8f9c2/check-runs. Confirm all required status checks show conclusion: success. [KEEP] 3. Verify commit hash 7a8f9c2…" </answer>

    • So the model did not really absorb the examples.
    • Possible reasons [CHECK]: learning rate or steps too low for a 0.069% adapter; a mismatch between the chat template and the gold text; only 156 examples.

4. GRPO: learning by trying and comparing

4.1 What it is

GRPO = Group Relative Policy Optimisation. It is reinforcement learning (RL): the model learns from scores instead of from copied answers. Each training step:

  1. Take one task. Let the model write G = 4 different answers (with randomness, so they differ).
  2. Score each answer with the reward function (§5). The scoring is fully automatic: plain code, no AI judge.
  3. Compute each answer's advantage: its score minus the group's average score.
  4. Make above-average answers more likely, and below-average answers less likely. The push is proportional to the advantage.

An illustration (not from the logs): four answers score 1.2, 0.4, 0.4 and 0.0. The average is 0.5. The advantages are +0.7, −0.1, −0.1 and −0.5. The first answer is reinforced most, the last is pushed down. The advantages always add up to zero: GRPO only cares which answer was better than its siblings.

4.2 How the update works in my code

  • Loss per answer = advantage × (cross-entropy of that answer) × (its number of tokens). Longer answers carry proportionally more signal. Only answer tokens count.
  • KL penalty (β = 0.04). KL divergence measures how far the trained model has moved from the original. A small penalty keeps it from drifting into nonsense.
    • The reference model is the same model with the adapter switched off (model.disable_adapter()), so no second copy is needed in memory.
    • Fact from the logs: the KL value was exactly 0.0 at every step of every run. The penalty never acted.
    • The report reads this as: the adapter changed so little that the two models looked identical at floating-point precision. Most behaviour changes in these runs therefore probably came from the prompt, not from learned weights [CHECK].
  • Gradient accumulation 4: 4 tasks × 4 answers = 16 answers per weight update.
  • Gradient clipping at 1.0: caps the update size. Without it, earlier runs saw losses of ±20 and reward collapse.
  • No "clip ε". PPO-style ratio clipping is not used. It's a plain policy gradient with a group baseline.

4.3 Settings

setting value
group size G 4
grad accumulation 4 (16 answers per update)
KL β 0.04
learning rate 5e-5 (2e-5 for GRPO after SFT)
steps 100 per run (200 for curriculum and GRPO after SFT)
temperature 0.9 (first runs), 1.1 (later), 1.3 (one run)
max new tokens 300 per answer
task sampling with replacement (the same task can repeat)

Temperature controls randomness when writing: higher means more varied, riskier answers.

4.4 Why GRPO and not PPO or DPO

  • PPO needs a second "critic" network to estimate how good each state is, plus ratio clipping. GRPO replaces the critic with the group average. That's simpler, and it fits on one GPU with the KL reference coming from the same model.
  • DPO learns from pairs of "preferred vs rejected" answers. There is no written reason in the repo for not using it [NOT FOUND]. A fact: the repo has an automatic reward, but no preference pairs.

Say it like this: "GRPO is RL without a critic. The model writes four answers, I score them, and each answer is judged against its siblings' average. That's cheap and stable for a small model."

5. The reward, part by part

The total score of one answer is the sum of these parts, with no extra weights. Only the directive bonus changed between runs.

part value what it rewards or punishes
Format +0.1 for <think>, +0.1 for <answer>; −0.2 if neither writing in the expected structure
Task 0 to +1 the share of the task's "must-do" criteria found as keywords (a criterion counts if ≥ 50% of its keywords appear)
Directive +1, +3 or +5 (by run) any [KEEP]/[COMPRESS]/[EVICT]/[REFOCUS] anywhere in the answer, right or wrong
Shield +1 if all shielded items appear; −2 for each one missing protecting critical facts
Thrift (length) 0 to −1: −0.5 × min((words − 150) / 100, 2) penalises answers over 150 words; it is the "token thrift" idea

With a +3 directive bonus, the best possible score is +5.2.

Weak spots, which I'd name myself:

  • The task score is keyword matching, so it can be gamed.
  • The directive bonus pays for any tag, not the right tag (see §8).
  • 93% of tasks have no shield, so the shield term rarely fires.

Four bugs fixed in the original reward script before the extended runs:

  1. The shield check was inverted.
  2. The shield-preservation bonus was missing.
  3. The directive bonus was missing.
  4. The run stopped at step 39: 156 tasks ÷ 4 = 39 batches. Fixed by sampling with replacement.

6. The exploration wall, the central finding

The idea in one line: RL can only strengthen a behaviour that already happens sometimes.

Why:

  • GRPO learns from differences between the 4 answers in a group.
  • If none of the 4 contains a directive, they all get the same directive score (0). The difference is zero, so this part of the reward sends no signal at all.
  • A bonus of +1, +3 or +5 makes no difference, because 5 × 0 is still 0.
  • Only when, by chance, one answer in a group contains a directive does that answer get a positive advantage and become more likely. If that chance is tiny, learning never starts.

What the logs show:

  • Bigger bonus:
    • bonus +1: 0.3% of answers had a directive;
    • bonus +3: 1.3%, and 0% in the last 20 steps;
    • bonus +5: 1.3%.
  • More randomness (temperature 1.3 + bonus 5): 0.5%; the first directive appeared only at step 79.
  • A worked example in the prompt: 3.0% early, 0% by the end.
  • Telling it "you MUST use a directive" ("REQUIRED: you MUST include exactly one memory directive … No directive = task failure."):
    • directives from step 2, 7.0% overall;
    • the best final score of all runs (rolling average +0.277).
  • Curriculum (must for 100 steps, then may for 100):
    • 9.2% in the "must" phase, 0.5% in the "may" phase;
    • the habit vanished when the instruction was removed;
    • the pre-set success test (> 10% directive use over steps 130–200) failed.
  • SFT, then GRPO: 0.5% overall, 0% at the end. It did not break the wall (§3.5).

Why the brief's "it worked after SFT" doesn't match:

  • SFT can break the wall only if it actually raises the starting chance of the behaviour.
  • My SFT loss never fell, and its data showed only [KEEP], so the chance stayed near zero.
  • The fix would be balanced gold data with all four directives, a working SFT run (falling loss, correct template), and a check that directive use rises before GRPO starts.

Say it like this: "The biggest lesson was the exploration wall. Rewarding a behaviour the model never tries does nothing, whatever the size of the reward. One word in the prompt, 'must' instead of 'may', did more than five times the reward. My SFT was meant to seed the habit permanently, but it didn't take, and I can explain why."

8. The reward-hacking story (the evaluator bug)

Reward hacking = the model, or simply a lucky answer, scores well by exploiting a flaw in how the score is computed, not by doing the task.

Where it showed up. SAMB ("Static Agentic Memory Benchmark") is an offline test.

  • It freezes agent trajectories into blocks, and each block has a gold directive.
  • The first grader (evaluate_samb.py) counted a block as correct if its gold directive string appeared anywhere in the model's output. That's a "bag of tags": it never checked which block got which directive.
  • Before the fix: an answer that just lists [KEEP][COMPRESS][EVICT][REFOCUS] plus the shielded words scored 1.0 on every metric (verified in SAMB/samb_review_and_recommendation.md).
  • The same flaw was in my GRPO reward: the directive bonus paid for any tag anywhere.

The fix.

  • Make the model answer per block (block_0: [EVICT] …) and parse that (parse_block_directives).
  • Score with Macro-F1. F1 balances precision ("of the times you said EVICT, how often was it right") and recall ("of the true EVICTs, how many you found"). Macro averages F1 over the four directive types equally, so always answering KEEP scores badly.

After the fix (Gemma 4 31B, live inference, 156 samples):

  • directive accuracy 24.9% (pure chance with four options is 25%);
  • Macro-F1 0.145;
  • 139 of 156 outputs (89%) gave the identical sequence KEEP, COMPRESS, EVICT, KEEP, whatever the content.

What that means: the model wasn't reading the content; the old grader hid that completely. (This measurement is on the 31B model, not the 4B models trained above.)

Say it like this: "My first evaluator could be beaten by printing every tag. The model would have looked perfect. After per-block parsing and Macro-F1 it scored at chance, 0.145 F1. Since then I attack my own grader before I trust any score."

9. Things that went wrong, and what I learned

  • The KL penalty was always 0.0. It never constrained anything; the adapter barely moved. Lesson: log KL early and check it is non-zero; consider a higher learning rate or an explicit log-probability ratio.
  • SFT loss stayed flat, and the data covered one directive. Lesson: check that demonstrations are balanced, and that SFT changes behaviour, before RL.
  • Format score was about −0.19 in every run. Most answers never used the <think>/<answer> tags the prompt asked for, even after SFT on tagged gold answers. Lesson: check that the structure you reward is reachable, and verify the chat template between data generation, SFT and RL [CHECK].
  • Keyword task reward and any-tag directive bonus are both gameable. Lesson: reward the correct action per block (Macro-F1), not the presence of a token.
  • Shield signal was sparse (11 of 156 tasks). Lesson: more shielded tasks, or a separate shield phase.
  • Group size 4 was never swept [NOT FOUND]. Small groups make rare behaviours even rarer in a batch.
  • No forgetting check [NOT FOUND]. The task reward fell after SFT (about 0.36 in Guardian → 0.21 after SFT).

11. Likely questions, with fuller answers

"Why didn't more reward fix it?" GRPO compares the answers it actually wrote. If no answer in a group has a directive, all four get the same directive score, so the difference that drives learning is zero. Raising the bonus from +1 to +5 multiplied zero: usage stayed around 1%. Only changing what the model tries (the "must" prompt) produced directives, from step 2.

"How did you pick group size?" G = 4, documented as "enough diversity for relative advantage", under a one-H100 memory budget (training ≈ 23 GB). I did not sweep G [NOT FOUND]. In hindsight, a larger G (8–16) would raise the chance that at least one answer per group shows a rare behaviour. That's directly relevant to the exploration wall.

"How do you know it didn't forget other skills?" I don't. There was no separate forgetting benchmark [NOT FOUND]. A warning sign: after SFT the task reward fell from about 0.36 (Guardian run) to 0.21. Before any next run I'd add a held-out general benchmark and track it per checkpoint.

"What would you do next?"

  1. Balanced gold data: all four directives, block-labelled, verified by the per-block grader.
  2. A working SFT run: correct chat template, loss that falls, and a measured rise in directive use before RL.
  3. GRPO with a reward for the correct directive (Macro-F1 per block), not for any tag; a mix of "must" and "may" prompts during training; a larger G.
  4. Check KL is non-zero from the first steps.

"What surprised you most?" That one word in the prompt ("must" instead of "may") beat five times the reward, a few-shot example and higher temperature. Second, that my evaluator could be beaten by printing every tag. That changed how I build evaluations.

"Was the 0.75 peak real?" It was the average of the first 3 steps, driven by the instruction. The honest numbers are the final 20-step average of +0.277 and the mean of 0.314 over 100 steps.

"Why a small 4B model?" To fit training on one H100 (QLoRA, about 23 GB), and because the target was efficient on-device-style agents.
